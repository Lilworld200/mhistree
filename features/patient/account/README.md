Auth inputs and floating-label backgrounds use pill radii (999px), with horizontal padding around the raised text.

`auth-field.tsx` supplies accessible nested labels that appear inside empty /auth inputs and animate onto the top outline on focus. Filled/autofilled fields keep the label raised; clearing and blurring returns it inside. Native date inputs track whether a date is present and hide their empty date template while idle. Shared CSS preserves rounded inputs, 16px input text, Manrope and the existing blue focus token; global reduced-motion rules disable animation. Input names, autocomplete, validation and original password handling remain intact.

`/auth` defaults to sign in. The submit button is followed by a horizontal row with “Forgot password?” on the left and conventional “Don’t have an account? Sign up” / “Have an account? Sign in” controls on the right on the same axis. Beneath them, a line–“Other options”–line divider exposes “Use a setup or recovery code”; redemption returns through restricted password setup, and the code form offers “Back to sign in.” Form fields remount on mode changes so passwords/codes do not carry into another form. Navigation is disabled during submission. The existing API operations and cookie-based setup resume remain unchanged.

`recovery-options.tsx` owns /recovery method selection: `email-recovery-form.tsx` requests a Supabase reset link, with private recovery code and identity-check guidance as alternatives. `/auth?method=code` opens code redemption directly; a restricted setup cookie takes priority. `app/auth/callback/route.ts` exchanges PKCE codes on the server using encrypted HttpOnly verifier cookies. `email-callback.tsx` renders the reset form on guarded /recovery/update or invalid-link guidance on /auth/confirm; no browser token parsing remains. SMS recovery is not configured. [Manual SMTP/callback setup](../../../docs/tasks/supabase-auth-setup.md).

T10 composes the T07/T08 identity/authentication services. `server.ts` owns idempotent self-enrollment, minimal profile reads, expected-version profile edits and optional unverified contacts. `entry.tsx` supplies registration, private-code redemption, patient password setup and login; `profile.tsx` supplies profile/contact edits and logout. `/api/auth/[operation]` and `/api/account` validate HTTP inputs and return bounded errors. `lib/http.ts` enforces configured Origin, JSON limits and HttpOnly/SameSite cookies; `lib/auth/patient.ts` guards patient routes. Every service verifies current sessions independently.

Email signup stores only a hashed browser-held enrollment key and a pending exact provider subject. Verified provider proof finalizes one person/account atomically. Invitation claims retain the approved original person and demographics. Contacts never transfer ownership; a primary Supabase login email cannot be removed as an ordinary optional contact. Passwords and provider tokens are not stored in app tables. Requests to Supabase email APIs do not prove inbox delivery; SMTP and callback configuration is owner-managed. Public IDs cannot sign in. Historical `beginRegistration` remains only for legacy integration evidence and is not invoked by the active signup route.

Current tests: tests/integration/supabase-email.test.ts (native PostgreSQL policy/race/failure checks plus optional real Supabase lifecycle using a temporary synthetic user). Older patient-account/auth tests require the historical Keycloak fixture and do not establish current Supabase delivery. Configuration: APP_ORIGIN, DATABASE_URL/DATABASE_SSL, NEXT_PUBLIC_SUPABASE_URL, publishable/anon key and server-only service role key. Never trust arbitrary forwarded headers.

Failure points: provider unavailable, expired/replaced setup, missing environment, retired sessions, profile version conflicts. T11 depends on the person mapping/session. T29 provides staff recovery UI; T33 owns production provider and contact delivery operations.
