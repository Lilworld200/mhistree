## Implementation

- `ai-chat/profile-context.ts` reads only the verified owning person's stored display name, nullable DOB and revision via the existing pre-RLS identity hook. No email inference. Publication rereads/compares under a row share lock held through the reply commit; an in-flight profile change retains the patient message and fails for explicit retry.
- `server.ts` detects the first patient turn after the current navigation checkpoint. It supplies a six-item/6000-character timeline overview plus independently bounded medication/allergy/current-state context, active messages and source dates. Subsequent unrelated chat stays selective. `context-plan.ts` treats timeline commands as overview requests. Overview selection ranks topic matches then source recency, so persistent lanes cannot consume all six slots before recent symptom reports.
- Extraction receives the exact immediately preceding assistant question (including its immutable message reference), as interpretation context separate from patient sources. Only a single direct current-presence symptom question with a matching subject permits a standalone negative resolution. Contact, negative, composite, ambiguous and unknown-subject questions cannot resolve a symptom. One uniquely identified older own-patient episode may enter eligible reports for a new-chat short answer; ambiguous competing episodes remain unlinked. Wider search candidates otherwise remain non-mutation context.
- Relations distinguish `same-report`, `same-incident`, `episode-update` and explicit `correction`. A known symptom status change mislabeled as a repeat is normalized to an episode update. Later updates keep their own supported time, including unknown stopping time, and never inherit original onset time. Retained repetitions keep source versions; separate episodes stay separate.
- Shared contribution validation accepts an optional internal JSON body `episodeUpdate` reference/version. It requires an authorized current patient-reported symptom head by the same author, an explicit validated context link and matching revision. It cannot combine an update with a correction or attach to another patient's/professional event. Existing transaction, source/item/operation idempotency, savepoints and short extraction lock remain; model calls remain outside transactions. No SQL migration is required: metadata uses existing JSON storage.
- `health-records/episode-state.ts` derives supplementary last-reported state by bounded forward traversal of explicit episode links, retaining the original event's status and all versions. Traversal follows retained link metadata across subsequent observation revisions. Retrieval includes the later report/date/uncertainty; it does not assert permanent recovery. Delivery rereads full bounded evidence, including episode updates, before and inside publication.
- Groq diagnostics now classify 429 causes into a small safe allowlist (day/minute tokens/requests) and optional numeric retry interval. Model names containing a slash survive the debugger allowlist. No raw upstream text, headers, account IDs, credentials, source text or reasoning is logged. No automatic retry/fallback was added.
