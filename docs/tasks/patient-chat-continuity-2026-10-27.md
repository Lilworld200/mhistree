## Ownership and flow

- `memory.ts` owns immutable source-cited private chunks, departing-message watermarks, per-conversation leases, source fingerprints and bounded recall. `chat_memory_links` records New chat's explicit previous conversation. `chat_memory_jobs` stores resumable coverage. `chat_memory_chunks` retains items, original message references/quotes/capture dates/zones, model and summary creation time. Chunking covers at most20 messages and16,000 content characters (one full oversized message is still accepted); no network request holds a database transaction.
- New chat creates a UUID immediately and starts preparation. One chunk per authenticated `prepare-memory` call, followed by another only while pending; another tab's active lease is polled at one second. Closed/navigated tabs stop driving work; opening that new conversation resumes from retained coverage. Successive New chat operations retain unfinished ancestor preparation; a persisted prepared checkpoint avoids walking old completed chains on every reply. Departure links must point to an older conversation, preventing dependency cycles. Provider/format failures release the lease and expose Retry preparation or explicit Continue with existing memory. Draft and voice receipt remain intact. A failed account/access check clears displayed history and offers no authority bypass.
- `generateReply` refuses linked, incomplete preparation unless the patient explicitly chooses `continueWithoutMemory`. Existing chats without links remain immediately usable. No unrelated old conversation is automatically summarized. Raw departing chat is read only for summary production; ordinary replies read stored derived chunks and the current conversation's existing bounded history.
- Recall selects up to8 relevant and8 recent chunks, ranks/deduplicates items, excludes already-loaded source messages, and fits8,000 serialized characters. It is explicitly incomplete, never an assertion of exhaustive lifetime recall. Stored chunks accumulate rather than recursively rewriting a large biography. Life context, preferences, patient reports, assistant advice, answered questions and open questions remain distinguishable. Citations must match actual supplied source text; patient facts cannot cite assistant messages. Gemini root-array and wrapper-object JSON both undergo the same strict item validation. Meaning still depends on model fidelity; exact quotes do not prove a paraphrase correct.
- Current timeline heads remain authoritative. Recall whose source message supports a superseded clinical contribution is omitted conservatively, even if that message also contains unrelated context. Context is rechecked after generation and inside reply publication. Summaries never invoke extraction, accept contributions, change medications or notify practitioners. RLS explicitly requires current owning patient account/context, including against broader merged-history reads; ordinary clinical consent grants no memory/title access.
- `temporal.ts` supplies server-now, source UTC capture, original IANA zone/local rendering and elapsed seconds. Timeline evidence now includes original source timezone; event precision stays unchanged. Date/time instructions distinguish upload/capture/event/summary times, midnight, DST, travel and unknown zones. Silence proves neither persistence nor recovery. No timer sends follow-ups; check-ins occur only when responding naturally.
- `titles.ts` uses a separate leased operation, eligible after two patient messages, with the first four messages and256 output tokens. Once saved, the title is reused. Naming failure retains the opening preview and can retry when reopened; replies/extraction/TTS are independent. Shared navigation shows the same title on desktop/mobile, with date available in its native tooltip. Previews redact obvious email/URL/UUID/long numeric identifiers; titles are private, and model instructions additionally avoid names/identifiers. No guarantee of automatic anonymization is claimed.
