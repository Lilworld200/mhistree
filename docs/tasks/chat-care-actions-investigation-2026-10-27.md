# Patient chat care-action investigation — 2026-10-27

Scope: owner requested diagnosis before implementation after a supplied chat example failed to contact a practitioner. Investigation used local source and existing synthetic tests only. No hosted patient/session lookup, provider call, message, booking, notification, migration, deployment or application behavior change. Original patient text is not copied into this record.

## Findings

1. Practitioner discovery exists. features/ai-chat/server.ts calls practitionerDiscovery before generation, inserts its result into authorized prompt context, and rechecks previously discovered recipients before publication. features/access/patient-controls.ts derives the patient from a verified session and returns up to100 currently eligible recipient names, connection/practitioner IDs, scope, revision and canMessage. This is server prefetch, not a model-callable tool. Eligibility filters approved professionals, active connections/accounts, current consent/category intersection, records.read/messages.send and applicable organization membership/assignment. A connection's existence alone does not guarantee inclusion.
2. Discovery failure and no eligible recipients differ. practitioner-discovery.ts propagates session/access failures but turns optional infrastructure/query failure into status=unavailable with safe diagnostic practitioner.discovery.failed. The transcript alone cannot establish whether this specific account supplied available recipients, an empty eligible list or unavailable discovery. No production inspection was performed.
3. There is no chat action executor. AIGateway.generate returns Promise<string>; GroqGateway submits messages and generation options without tools/tool_choice, requires a finished textual reply and has no tool-call dispatch loop. /api/chat supports conversation/send/generate/cancel/memory/title operations only. Its send action stores private AI-chat patient text; it does not call sendCareMessage. ChatView has no practitioner-recipient/draft review/send or appointment proposal workflow.
4. Prompt explicitly blocks action claims: patient-prompt.ts says there is no tool to send, flag, notify, book or publish, directs patient-reviewed sending through Care inbox, and forbids pretending anyone was contacted. This matches existing owner boundaries around private-chat isolation and reviewed handoff. Refusing to claim contact is therefore structurally expected, not evidence the model lacks reasoning or that changing providers would enable actions.
5. Actual services are separate: app/api/care/route.ts dispatches message to messaging.sendCareMessage and book to appointments.requestAppointment. The patient Care inbox selects a connection and explicitly submits reviewed content; appointment request requires a provider/slot/timezone and current authorization. Messaging validates scope/context, author and idempotency, stores the message, audit and outbox atomically. Stored is not proof read or acted on. These operations are available to their screens, not to chat generation.
6. Existing practitioner blue dots derive from saved incoming unread care messages in practitioner/notifications.ts. Private chat alone creates none. There is no email/push delivery daemon established by this path. A reviewed care-message save can drive existing inbox indicators; a standalone chat notification or emergency handoff executor does not exist. The chat header bell remains unavailable under the existing product decision.
7. Separate response-quality defects in the supplied example: the draft turned a proposed medication action into asserted prior use; the earlier reply also assumed tablets had already been taken. Neither is supported by the reported conditional wording. The reply did not make useful use of a verified recipient or provide a concrete inbox next step. Its offer to help send is misleading given the absent workflow. Ambiguous medication wording should be clarified rather than silently treated as confirmed use. Whether a particular medication-risk response is clinically adequate is not certified by this source review.
8. Coverage gap: existing discovery tests check isolation, eligibility, optional failure and revocation; they deliberately assert ordinary chat does not write care_messages. patient-chat-voice.test.ts live tone cases instantiate GeminiGateway directly and prohibit unsupported action offers. Current groq-live.test.ts covers generic wind-down/JSON/title and speech, not the supplied medication/contact intent. No existing verified end-to-end chat-to-reviewed-care-message or chat-to-appointment action was found.
