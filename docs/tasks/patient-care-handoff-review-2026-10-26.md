# Patient AI to practitioner handoff: code review and proposed change

Status: investigation and implementation design, not an implemented handoff. Owner is considering a patient AI/practitioner AI/Care inbox/Health integration. During review the owner explicitly selected: patient reviews the summary and chooses an eligible practitioner before a non-emergency handoff is sent. Existing local source edits were inspected and preserved. No hosted access, model calls, migrations or product source edits were performed in this review.

## Existing pieces and observed defects

Patient AI server persists original messages, retrieves authorized evidence and generates/rechecks buffered replies. Extraction independently accepts reports into timeline/Health. Practitioner assistance reads authorized records and its own previous runs; it does not currently retrieve patient-practitioner care messages. Messaging already provides explicit-context authorization, durable ordering, idempotent sends, audit/outbox and message-read positions. Daily inbox projects unread counts. Notifications have event_key/read_at and RLS enabled, but no runtime read policy/grant in tracked migrations. App navigation does not currently share event badges across these surfaces.

Recent local edits add getConnectedPractitionersInAccess in access/patient-controls, feed it through AI retrieval, add symptom guidance, render dots and synthesize a handoverSummary from one latest accepted report. Findings:

1. The lookup joins accounts/persons/organizations inside withAccess's restricted runtime transaction. Existing timeline tests now fail with permission denied for table accounts; the query is not executable under current grants. Preserve least privilege: implement a narrowly authorized recipient projection, rather than granting generic identity-table access or moving arbitrary clinical reads outside RLS.
2. workspace.ts's pendingEscalation query reads notifications from that same restricted role. Existing workspace tests fail with permission denied for table notifications and the API returns503. Correctly scoped access needs its own policy/projection, with current actor/context checks. Do not disable RLS to make dots work.
3. can_participate in patient context checks the patient's ability to use messaging through the connection. It does not prove the receiving practitioner's current messages.send privilege or category-specific record access. Organization connection rows are not individual assigned recipients. Reusing eligibleCareProviders unchanged is also wrong: it is appointment-privilege based.
4. Recent patient report within48 hours is neither evidence of clinical need nor a per-practitioner unread checkpoint. It can be a routine activity, late report of an old event or correction. Current pendingEscalation accepts every unread notification kind, including appointment/request/message notifications. No code advances notification read_at, so the new dots do not have a complete clearing path.
5. handoverSummary interpolates one report's category/body.text; it is neither generated nor patient reviewed, and can omit context. The UI calls it Patient Summary from AI. It needs truthful provenance and a distinct stored reviewed handoff, rather than a raw latest-report proxy.
6. No handoff proposal/preview/recipient selection/send action or durable care-status lifecycle exists. Existing message sends are manual. Prompt text alone cannot send a message or confirm delivery. Health summary is still the current UI label.
7. GeminiGateway/AIGateway generate returns text only, supports no tool declarations, functionCall/functionResponse loop or thought-signature round trip. The patient prompt explicitly says No tool calls. Passing connectedPractitioners in context is server prefetch, not a callable tool. The pre-publication evidence check compares clinical evidence IDs, not changed recipient eligibility.
8. The model sees only the context explicitly supplied on each request. Neither patient nor practitioner AI currently receives shared care messages through this retrieval path; shared model names do not imply shared memory.

## Proposed workflow

Keep three outcomes, not a forced choice between sending to a doctor and home advice: ordinary conversation/general support; non-emergency proposed handoff; immediate-danger guidance. Clinical urgency and routing are different decisions. A help request does not automatically send anything, and lack of a connected clinician must not cause reassuring or delaying advice. General measures must fit known context and uncertainty; hardcoded food/hydration/exercise lists are not universally safe. Clinical escalation wording/fixtures still require the project's human safety release review.

1. Continue durable message capture and independent report extraction. Ask a useful clarifying question when needed; do not infer a diagnosis or issue status from casual wording.
2. Expose one read-only getConnectedPractitioners tool. The server derives patient identity from the verified session, never model-supplied person/account IDs. Return only bounded currently eligible recipients, connection/context reference, minimum display identity and allowed categories/capabilities. Validate professional/account status, explicit direct path or approved organization+active membership+assignment, relevant recipient privileges, current consent categories/exclusions and provenance. Keep independent contexts separate. No recipient secrets or arbitrary SQL/function execution.
3. Extend the gateway with a bounded allowlisted tool round trip, preserving Gemini model parts and signatures, cancellation/deadline/token limits and safe logs. Unknown/malformed tool calls fail closed. Keep read-only discovery separate from sending; model output must never directly authorize a notification or clinical write. Revalidate authority after generation and on confirmation.
4. Generate a source-linked draft for a selected eligible recipient using only information shareable in that context. Offer recipient selection before final preview so a broader patient context cannot leak through a summary. Show reported concern, occurrence/capture times and uncertainty, relevant permitted background and patient's request. Patient can edit, cancel or confirm. Persist the exact approved text/version and chosen recipient/context; exclude unrelated private AI messages. A draft neither notifies a practitioner nor becomes a diagnosis.
5. Confirm through one idempotent authenticated operation, rechecking recipient/scope/version and source visibility. Atomically store reviewed handoff, initial care-message reference, status transition, audit and outbox. If receipt acknowledgement is uncertain, retry by stable request key/status rather than create a second referral. Never claim a practitioner was notified before durable success, or that stored means read/accepted/clinically reviewed. Existing database acquisition-only retry rules remain intact.
6. Practitioner Care inbox shows the reviewed AI-assisted patient summary and patient-practitioner messages. Practitioner replies directly through existing messaging. Patient sees their own AI conversation and their own shared care conversation, with a linked view if desired. Practitioner cannot open private patient-AI transcripts. Patient AI may retrieve bounded currently authorized care messages, explicitly attributed; practitioner AI may retrieve only its permitted care thread, approved handoff and existing authorized records. Neither direction leaks practitioner private notes/drafts/internal AI dialogue.
7. Rename the patient-detail Health summary entry to Health. Show source-linked reported concerns, medications/allergies/ongoing issues, timestamps/uncertainty and care-request status. Separate clinical status (reported active/resolved/unknown, supported by evidence) from workflow status (draft/sent/awaiting reply/in progress/closed). A symptom and a care handoff are distinct linked records; reuse accepted report IDs and shared clinical services to avoid duplicate timeline/state writes.

## Notification contract

One durable event identity drives relevant projections rather than three separate alerts. A confirmed handoff can affect Care inbox and patient-specific Ask Mhistree; an accepted clinical report can affect Health within its permitted category. A routine report may create a Health update without a handoff. An appointment must not create an AI-care alert. Patient messages, practitioner replies and clinical corrections have their own typed events.

Use per-recipient/per-surface acknowledgement checkpoints referencing exact event/version, not a48-hour recency timer. Viewing Health acknowledges shown Health updates; reading the thread advances only displayed messages/handoffs, not clinical task completion; opening Ask Mhistree need not mark care clinically reviewed. Newer updates remain unread. Add scoped counts/booleans to existing focused snapshots and navigation aggregation, preserving the single non-overlapping15-second refresh owner. Any faster delivery must preserve current-access filtering and must not add independent polling loops. Revocation/narrowing/removal invalidates eligible recipients, displayed data, queued delivery and AI publication; reconnection does not resume paused care.

## Implementation order and acceptance

1. Repair the two current restricted-role read regressions without broad grants; test owner/other actor/revoked/narrowed/category/direct/organization boundaries.
2. Define and migrate minimal durable handoff/version/recipient/status and scoped acknowledgement records, with constraints, RLS and event-key deduplication. Reuse existing messages/audit/outbox/clinical services; no automatic diagnosis or prescription.
3. Add read-only discovery tool, structured draft generation, patient recipient/preview/edit/confirm and cancellation. Preserve failed input; test forged recipient/source IDs and scope changes during generation/confirmation.
4. Integrate care-thread context into each AI under its separate authorization rules. Test transcript/private-note isolation, injection, provenance and bounded history.
5. Wire Health/Care inbox/Ask Mhistree and app-navigation dots, status and acknowledgement. Test independent surfaces, duplicate/out-of-order events, disconnected clients and no duplicate polling.
6. Run deterministic gateway/clinical safety fixtures plus real local PostgreSQL and UI journeys. Cover routine conversation/no handoff, explicit contact/review/send, no eligible recipient, urgent-help response without waiting, provider failure, duplicate confirm, revoke after preview, staff removal, and uncertain delivery. Live model semantic/clinical review remains separate from structural tests.
