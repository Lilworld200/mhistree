## Implementation map

- `clinical-care/proposal-review.tsx`: extracted shared editable text review with category, occurrence precision, status, medication identity/dose/frequency/use dates and source spans. Missing consequential details block publication. `patient-assistant.tsx` supports the same direct/organization transports and optionally an own canonical care-message origin. Its patient-profile label/panel/accessibility name is **Talk to Mhistree**.
- `practitioner/workspace-view.tsx`: Care notes explicitly selects Private note or Add to patient record. Record preparation reuses practitionerAssistance and shared review; existing author-private notes/reminders/drafts remain available. Own inbox findings can be prepared for separate reviewed publication. Message Send alone never saves a clinical finding. Stable client operation keys survive failed note/message requests.
- `ai-chat/practitioner.ts` and `clinical-care/ai-entry.ts`: verify own source message and current context/revision; suspected findings remain suspected. Optional additional allergy history is a limitation, not a prerequisite for recording an explicitly suspected finding. A model upgrade from suspected to confirmed is rejected. Only reviewed publication creates a finalized clinical attachment in the same transaction; private-note saving does not. Retries attach once.
- `clinical-care/medication-recommendations.ts`: separate reviewed direct/organization message/prescription recommendation sources, independent disposition/use-state fields and an explicit closed-initiation flag, pending/planned/taking/stopped/declined/dismissed/withdrawn states, explicit patient commitment metadata and dated planned/use fields. Clear patient statements create separate linked patient-report events through the existing atomic kernel. Interpretation tolerates smart apostrophes without rewriting the original source, and explicit relative start dates use the persisted message capture clock. Several recommendation sources for the same exact medicine share the daily follow-up limit; no prescribed dose or regimen is inferred from a named-medicine commitment. No taking state follows prescribing, a practitioner yes, a contact negative or an ambiguous medicine name. Short answers bind to the exact preceding delivered medication question. Conservative deterministic capture leaves unsupported wording to normal extraction/clarification rather than guessing.
- `ai-chat/server.ts`: bounded pending recommendation context in the same ordinary generation call. A relevant due medicine may receive an exact initiation/plan question only when it does not stack another question or interrupt urgent/contact workflow; actual published delivery is recorded atomically and serialized per patient. No initiation notification daemon. Confirmed use/refusal/dismissal/withdrawal ends initiation follow-ups. `extraction/server.ts` reuses the accepted commitment event for that medicine while still processing other health details in the submitted message.
- `health-records`: planned is not-started plus commitment; current Health suppresses earlier linked use projections in favor of the latest recommendation-linked event, while every event remains in timeline/history. Recommendations/plans are visible separately and can have follow-ups dismissed. Prescriptions remain distinct from use.
- `ai-chat/memory.ts`: handoffSummary and departure prepareMemory share the same private session snapshot, lease and source checkpoint. Canonical direct care exchanges never enter these source messages. Shared text labels patient reports/context/preferences and patient/Mhistree open questions separately, with capture dates. Handoff preparation retains an immutable private source-reference/fingerprint checkpoint so later replacement of the private live summary cannot break an unchanged reviewed retry. Corrected source evidence prevents a new send from that checkpoint. Summary failure keeps the draft; UI offers Retry or explicit sending without the attachment. The patient can edit/remove the proposed attachment before Send.
- `messaging/server.ts` / care delivery: summary attachment is copied into each canonical message and frozen with per-destination reviewed text. Current recipient checks and partial-delivery receipts remain; successful copies are never resent. Canonical inbox and integrated chat show the immutable summary and any separately finalized clinical attachment. Neither raw private transcript nor live summary is exposed.
- `messaging/connected-chat.ts`, `/api/chat/connected-care`, `ai-chat/use-connected-care.ts`: patient-owned per-view activity, scoped45-second presence and immutable message placement. An account advisory lock plus unique message key assigns incoming replies once to the most recently active visible session across devices; without one, the next opened session receives them. Only messages after a patient-originated linked exchange participate; no bulk historical import. Presence identifies the exact eligible practitioner and distinguishes patients from organization colleagues. Presentation is bounded; canonical Care inbox retains the thread.
- Chat clearly attributes practitioner/patient/Mhistree messages and links the originating exchange. A named currently eligible recipient must be selected for direct mode. Direct sends use canonical messaging and create no AI generation, extraction job or private-summary source. Clear medicine reports about known recommendation medicines still update patient-reported Health through the shared atomic source kernel. Canonical care-message IDs, original clocks and exact displayed reply-to references preserve provenance; stale/unseen questions cannot establish use. The patient can explicitly return to Mhistree. Displayed-message acknowledgement is bounded by the exact displayed care sequence. Current authority/revision checks apply on every send/read/sync. An explicit care access denial immediately clears the restricted care presentation and recipient while preserving the unsent input. Failed optional care presentation does not block private AI conversation.
- Reviewed microphone sends in direct mode retain original transcript metadata on canonical messages. The server verifies the encrypted account/session receipt and rejects reuse across private/direct chat, preserving explicit reviewed Send and transient raw audio.
