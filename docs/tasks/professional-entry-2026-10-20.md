## Flow and owners

1. Patient /auth retains its ordinary signup/sign-in, setup/recovery and password-reset links. Other options adds Healthcare professionals and organizations -> /auth/professional.
2. Chooser exposes Healthcare professional -> /auth/professional/practitioner and Organization -> /auth/professional/organization. Each has distinct headings and can sign in or register through the existing account service. The choices grant no role.
3. Authenticated existing patients enter the corresponding reviewed application without creating a second person/account. Existing approved professionals continue to their dashboard. Organization applications/status reuse the existing human administrator account; an organization is not a separate password identity.
4. `features/auth/entry-path.ts` accepts only practitioner|organization fixed paths. Signup transport removes entry intent before strict identity enrollment, retaining routing intent in a one-hour HttpOnly/SameSite cookie. Existing verified signup callback consumes it; missing/invalid intent returns /chat. Login returns the selected allowlisted path and clears stale intent. Cookie tampering cannot grant a role or redirect externally. PKCE/proof consumption, origin protection and app-session verification remain unchanged. Email verification requires the existing configured delivery/callback environment; tests do not prove inbox delivery.
5. `workspace-access.ts` verifies current session and queries only own professional status, organization application, active membership or valid targeted invitation. `authenticated-shell.tsx` supplies booleans to both desktop/mobile navigation and guards professional layouts. Default AppShell has no professional/org links. Application/status navigation is distinct from approved clinical workspace; targeted invitations retain a route to acceptance. Clinical/organizational services still independently enforce current qualification, consent, assignment and privilege. Navigation eligibility is not clinical authority and layouts are not the sole security boundary.
6. `currentPatient` returns null for absent/retired credentials on public entry, avoiding a self-redirect loop for stale cookies. Protected `requirePatient` retains redirects, with professional layouts selecting the professional login destination.

New pages use existing account-stage/card/logo/button/form tokens. Enrollment cards widen to720px for existing application forms and remove duplicate inner page padding. Patient layout/colors unchanged. Existing passwords/contacts are not fabricated; professional or organization approval is never automatic. Old clinical/organization services are reused, not forked.
