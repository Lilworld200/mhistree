## Step-by-step behavior and ownership

1. Verify current patient session and fetch the minimum eligible message-recipient projection. Optional lookup failure remains distinct from available-but-empty. Safe diagnostics record status/count/bounded only. The existing discovery query now has a capability parameter for separate appointment eligibility and takes shared locks on current connection/account/professional rows and applicable organization/membership/assignment rows. Locks end before model requests.
2. Generate conversational text and an optional strict JSON message/appointment proposal in the same provider call. Production Groq20B uses strict JSON Schema; explicit Gemini rollback uses its JSON Schema adapter. Existing text-only injected/test adapters remain compatible but cannot propose actions. The response parser rejects malformed output without provider retries. Medication wording preserves proposed versus actual use; unclear drugs/recipients require clarification. No server tool dispatch loop, built-in web tool or extra model router.
3. Publish natural assistant text and an optional private proposal atomically after current source/memory/recipient rechecks. Models can only suggest recipients in the supplied eligible list. Longer natural-language requests start with an unselected destination even if the model picks one; the patient selects the destination explicitly. Only a standalone exact unique recipient name (such as a clarification answer) may preselect its matching eligible destination. No implicit context switch or guessed name is accepted. Initial shared text is a literal copy of the latest submitted patient question with a neutral introduction, not the model draft. Overlong questions are not truncated; an empty draft requires the patient to write the reviewed question. This conservative choice followed observed live-model recipient/regimen errors. History returns proposal metadata in a separate field, never injected into displayed/spoken text. Up to four actual saved care outcomes can ground subsequent replies without asserting reading or acceptance.
4. Show a review card inside its owning reply: current recipient, exact editable message, Send message, Dismiss and Refresh options. Organization threads are labeled shared care-team destinations. Proposal edits save after500ms and serialize; Send waits for the reviewed edit's returned version. Failed unsaved changes survive conversation switching in tab memory, with an unload warning; no localStorage/sessionStorage. Saved private drafts survive page refresh. Multi-tab conflicts preserve text and offer explicit reload, with confirmation before replacing unsaved edits. A revoked recipient cannot receive a message, but unchanged-destination private content edits can still save; Clear previous recipient permits a fresh explicit choice.
5. Confirm in one authorized transaction. Lock the private proposal, compare its revision, require a currently eligible recipient and the connection revision reviewed by the patient, then call shared sendCareMessageInAccess. Care message, audit/outbox and completed proposal commit or roll back together. Stable operation keys and stored results make duplicate/lost-response confirmations idempotent. Never equate stored with read, clinical review, task completion or a response deadline. Only actual care messages drive existing unread indicators; no private proposal produces them.
6. For explicit appointment requests, use separate appointments.manage eligibility. Offer the first100 advertised30-minute slots within90days, aligned to availability start/timezone and excluding loaded practitioner conflicts. Empty availability is explained rather than fabricating a slot; existing Appointments remains available. Slot selection is explicit, not inferred from speech or model dates. Confirmation rechecks advertised availability/current recipient and uses requestAppointmentInAccess with existing overlap/idempotency/audit rules. State is requested, never automatically accepted. Message and appointment confirmations are independent.
7. Preserve existing extraction, source clocks, current-access checks, Groq voice and Google embedding configuration. Proposals never enter clinical extraction, private summaries, practitioner retrieval or speech. Actual submitted care text is the patient's reviewed text, not the full private transcript.
