# Authentication contract v1 — T08

## Current MVP provider - 2026-10-14

Owner switched to Supabase Auth, requiring email/password for self-signup and activation; no-email authentication is explicitly deferred. Staff may still create an unactivated Person without credentials. `lib/auth/config.ts` selects Supabase; Keycloak code/tests below are retained historical foundation evidence and are not the production route provider.

`features/auth/email.ts` owns signup, verified activation, login, email reset and reviewed setup. Signup stores a pending exact Supabase subject plus source-bound enrollment; no Person/Account is created for self-signup before verified proof. Staff setup records a target Person under the one-time setup credential. Provider `getUser` validates the exact bearer and verified email before binding; email similarity and user_metadata never authorize linking. Existing unmapped Supabase users enter identity review rather than creating duplicate people.

App access continues using hashed opaque HttpOnly/SameSite sessions and current account epochs, capped at the Supabase access-token expiry. Raw provider tokens are never persisted in app tables or logs. No silent browser Supabase session grants private clinical access. Logout ends the app session. Supabase password reset globally signs out refresh sessions, then updates the exact verified subject and retires every local app session. A provider-issued-before cutoff rejects stale provider JWTs after reset. Callback confirmation proof is single-use; reset proof is fresh (10 minutes), single-use and account-bound, with explicit recovery-pending denial if provider work fails. Supabase's remaining access JWT lifetime is not claimed revoked remotely.

Assisted recovery requires the existing reviewed code and matching current Supabase login email; admin password update does not change patient ownership. Retirement disables the Supabase identity in addition to retiring local sessions; disabling is not claimed to recall already delivered JWTs. A reviewed existing Keycloak account can transition only using its authorized recovery code plus verified Supabase email, retaining the same account/person and an immutable provider-transition record. No global historical-account migration was performed.

Configuration: intended Mhistree Supabase URL, publishable/legacy anon key, server-only service role key, private DATABASE_URL, APP_ORIGIN. Custom SMTP must permit real recipients; allow `${APP_ORIGIN}/auth/confirm` and `${APP_ORIGIN}/recovery/update` and retain email confirmation. Browser callback consumes the default Supabase implicit fragment, clears it immediately and sends proof to the guarded server endpoint. Do not put credentials in query strings. Rate limits, Origin/CSRF checks and bounded JSON apply to every mutation.

## Historical Keycloak foundation (superseded provider choice)

2026-10-14 owner clarification, documentation only: creation without email and password is restricted to authorized organizations/practitioners, not ordinary patient self-signup. Staff-created identities are not automatically activated logins, and staff never choose passwords. Current implementation has not been changed; later contactless activation/provider implications still need reconciliation. No authentication migration is authorized by this clarification.

Local implementation: Keycloak26.8 supported username/password with PostgreSQL registry. Person ID, public alias, provider subject and opaque login username are distinct. No email or phone is synthesized. Email login is eligible only with an independently verified app Contact and matching provider-owned email; contact enrollment/verification transport is T10. A public locator alone is never accepted as login.

Issue: verified staff session + context + designated auth.activate/auth.recover privilege + restricted evidence reference. Returns private code once. Unknown fields (including password/role) rejected. Activation replacement and recovery are distinct operations.20-minute code,10-minute setup bearer. These are adjustable implementation defaults, not clinical retention policy. Errors for invalid/expired/replayed/replaced codes are uniformly TOKEN_INVALID to avoid enumeration. Trusted transport network key and token/identifier counters enforce bounds; provider brute-force protection is enabled.

Redeem: atomic conditional state transition; concurrent attempts have one winner. Creates setup-only hashed bearer. Patient chooses password (12–128 characters, no trimming); provider performs credential hashing. Stable reserved username and per-person lock make provider retry/replacement coherent. Success binds one Account to the existing Person and advances session epoch. Staff issuance does not create a patient session.

Login: confidential provider request, verify signature/issuer/expiry/authorized-party using jose and provider JWKS, check current account status/epoch, then create random HttpOnly-ready application session whose expiry is capped by provider token. Local registry is session authority after this exchange; every protected request checks account state, epoch, retirement and expiry. No provider token is returned to UI or stored in plaintext. Logout retires the selected app session. Password recovery retires all old local sessions immediately, with durable provider reconciliation if the external call fails. Setup retries that reconciliation before reactivation.

Provider outage is PROVIDER_UNAVAILABLE and must not be shown as activation success. No raw HTTP provider response or secret is logged. Restricted identity evidence is referenced in auth tables, not ordinary clinical views. Migrations preserve credential replacement lineage and audit events.

Official references inspected2026-10-10: [Keycloak local setup](https://www.keycloak.org/getting-started/getting-started-zip), [server administration and direct grants](https://www.keycloak.org/docs/latest/server_admin/index.html), [OIDC endpoints](https://www.keycloak.org/securing-apps/oidc-layers). The adapter is replaceable; local real-provider proof is not hosted-production approval. Production hardening must address TLS, service-account scope/no impersonation grants, server backup/monitoring and migration of any old email accounts. Direct grants do not provide browser SSO/MFA; those future needs require a reviewed provider-hosted authorization-code flow, not silent expansion of this adapter.
